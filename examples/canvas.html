The canvas tier: same map, no DOM per feature

10,000 generated cells. On SVG that is 10,000 <path> elements; on canvas it is one <canvas>. Switch backends and watch the element count in the status line, then hover and click either way: the tier has no DOM to receive a pointer event, so hit testing goes through an R-tree of feature bounds plus an exact isPointInPath, and behaves the same as the SVG map does.

What this actually buys, measured

Worth saying plainly, because it is not what "add a canvas renderer" suggests: panning does not get faster. SVG's camera is already one transform on one group, so it is O(1) in the feature count. Measured in Chromium on this page, both tiers sit near 9 ms at 10,000 features; canvas is 9.8 ms at 20,000 and leaves the 16 ms budget above about 30,000. Recolouring is slower on canvas too, since it remerges and re-rasterises where SVG rewrites fill attributes.

What canvas removes is the DOM: sixteen elements instead of twenty thousand. That is memory, style recalculation and accessibility-tree weight the map imposes on the whole page, not just on its own frames, which is why 'auto' promotes on element count rather than on frame time, and why the threshold is 20,000 rather than something flattering. Press "Pan 60 frames" in either mode and compare.

The tier takes the layers whose element count scales with geometry: feature fills, arcs, routes, the sphere and the graticule. Labels, annotations, bubbles, markers, the selection box and the accessibility tree stay SVG in both tiers. Text on canvas is not selectable, translatable or reachable by a screen reader, and point marks are already bounded by clustering and already hit-tested by computation rather than by DOM. Toggle the labels below: they are the same collision-avoiding SVG text either way. 

{
  chart: {
    renderer: 'auto',         // 'svg' | 'canvas' | 'webgl'
    rendererThreshold: 20000, // geometry marks at which 'auto' promotes
  },
}
